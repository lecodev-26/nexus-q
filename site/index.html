/ overview

What is NEXUS-Q?

A post-quantum cryptographic security engine. It is a library first: a Rust core that does all the cryptography, with a command line, an HTTP server and language SDKs layered on top. It is meant to be embedded in applications and servers that need to protect secrets for the long term.

Data

Authenticated encryption of files and streams, with envelope encryption (format F-02) so payloads are protected under a key that is itself protected.

Keys

The full key lifecycle: generation, rotation, revocation and destruction, stored in an encrypted vault (format F-01) with atomic writes.

Identities

Digital signatures, signature verification, identity rotation and revocation, and signed verifiable credentials.

Why post-quantum?

Large quantum computers would break the public-key schemes in wide use today (RSA, elliptic curves), and data recorded now could be decrypted later. NEXUS-Q uses the NIST-standardized lattice algorithms ML-KEM and ML-DSA, and pairs the key exchange with classical X25519 as a hybrid.

The golden rule

We do not invent cryptography. Every primitive is a standardized algorithm implemented by a maintained library. Deviations need a written architecture decision record. The project also states plainly that it does not claim every dependency has been independently audited.

/ how it works

From password to protected data

Every operation goes through the same building blocks. Policy decides who may act, the vault guards the keys, and security-relevant events are written to an audit log that detects tampering.

01

Unlock the vault

A password goes through Argon2id to unlock the encrypted vault. The vault holds keys at rest and is written atomically.

02

Manage keys

Generate, rotate, revoke and destroy keys. Secrets are zeroized in memory when they are no longer needed.

03

Encrypt or sign

Hybrid ML-KEM + X25519 for key exchange, AES-256-GCM or ChaCha20-Poly1305 for data, Ed25519, ML-DSA-65 or SLH-DSA for signatures.

04

Enforce policy

A deny-by-default policy engine decides which actions are allowed before they happen.

05

Audit everything

An HMAC-authenticated audit log with rollback anchoring makes tampering and truncation detectable.

Library first

The core is a Rust library. The CLI, the server and the SDKs are thin layers on top and contain no cryptography of their own.

Hardware-agnostic boundary

Provider traits exist for software, TPM, HSM, Secure Element and RISC-V. Hardware isolation is only claimed when a provider is implemented and tested. The default software backend does not provide it.

Security from the ground up

The threat model and the cryptographic rules were written before the code, and they are part of the repository.

Observability

Request IDs, aggregate metrics, health and readiness probes. Secrets are kept out of logs.

/ cryptography

Six families, nothing else

The core is only allowed to use six families of primitives. Anything outside them, such as raw RSA or custom MACs, is forbidden by the project's own rules.

FamilyPurposeImplemented
RandomnessEntropy for keys, nonces and saltsOS CSPRNG, plus TRNG support with health checks and mixing
HashingDigests and commitmentsSHA-2, SHA-3
KDFPasswords and key material to keysArgon2id, HKDF
AEADSymmetric authenticated encryptionAES-256-GCM, ChaCha20-Poly1305
KEMPost-quantum key encapsulationML-KEM-768 and ML-KEM-1024, hybrid with X25519
SignaturesAuthenticity and non-repudiationEd25519, ML-DSA-65, SLH-DSA-SHAKE-128f

Planned algorithms are never described as available until they are implemented and tested. The reference document is docs/CRYPTOGRAPHY.md.

/ security posture

What we claim, and what we do not

Cryptographic software earns trust slowly. This is the project's own statement of its current assurance level.

Claimed and evidenced

  • Standardized algorithms only, through maintained libraries
  • Secrets zeroized when no longer needed
  • Tamper-evident, HMAC-authenticated audit log
  • Deny-by-default policy engine
  • Security CI gates, SDK CI, benchmark CI and fuzz targets
  • Published threat model and security model
  • Dual license: MIT or Apache-2.0

Not claimed

  • Independent external security audit
  • FIPS validation or Common Criteria certification
  • Formal verification
  • Production readiness
  • Security endorsement, audit, or production readiness implied by publication to a package registry
  • Hardware isolation from the default software backend
  • Performance leadership

Found a vulnerability? Report it privately through GitHub Security Advisories, not a public issue. See SECURITY.md.

/ quick start

Build it and use it

To build current main, use Rust 1.88 or newer. Linux and Android/Termux are the environments exercised most; published packages may have different toolchain requirements.

1 · Build

# clone and build the workspace
git clone https://github.com/lecodev-26/nexus-q
cd nexus-q
cargo build --workspace --release

2 · Create a vault

./target/release/nexusq vault create ./example.nqv
./target/release/nexusq vault status ./example.nqv
./target/release/nexusq health

3 · Generate a key

./target/release/nexusq key generate ./example.nqv \
  --algorithm ed25519 --purpose sign \
  --password-file ./password.txt
./target/release/nexusq key list ./example.nqv

4 · Encrypt and decrypt data

./target/release/nexusq data encrypt ./example.nqv \
  --key-id <key-id> ./secret.txt
./target/release/nexusq data decrypt ./example.nqv \
  ./secret.txt.nqx ./secret.out

Prefer --password-file over typing a password on the command line, and never commit that file. The full command list is in the CLI guide. Server setup is in docs/SERVER.md.

NEXUS-Q is built in the open and is still young. The most useful help right now is scrutiny: more eyes, more hardware and more honest measurements. Some of these need no cryptography background.

Run the Arena on your hardware

Reproduce the benchmark numbers on your own CPU and share what you find in an issue. Differences between machines affect reproducibility; treat local results as observations, not official gate evidence. Start with arena/README.md.

Review the threat model

Read the threat model and the security model, and tell us what is missing or wrong. A gap in the reasoning is worth more than praise.

Test on your platform

Build the workspace and run the tests on Linux, Android/Termux or RISC-V, and report anything that fails or behaves differently.

/ faq

Questions people ask

Is NEXUS-Q ready for production?

The project does not claim production readiness. It is an engineering project with strong CI gates, but there has been no independent audit or certification. Evaluate it, review it, and treat it accordingly.

Has it been audited?

No independent external audit has been completed, and none is implied by a GitHub release. The project states it will link a public evidence package from the repository if one exists.

How does NEXUS-Q perform compared with AWS-LC?

Performance depends on the backend and operation, so a blanket claim that NEXUS-Q is slower would be misleading. The default build uses RustCrypto; the opt-in native backend passed the reviewed CI gate of at most 1.5× AWS-LC latency for both median and p95 across all nine measured ML-KEM and ML-DSA operations. That gate allows some operations to be slower; it does not claim the native backend is faster in every case, and primitive benchmarks are not end-to-end application benchmarks.

Why combine ML-KEM with X25519?

A hybrid keeps the key exchange protected as long as at least one of the two schemes holds up. That is the usual reasoning for hybrids while post-quantum algorithms are still young in deployment.

Can I use it from Python, Go, C, PHP or Ruby?

Yes. Python is published on PyPI; Go is available via pkg.go.dev; PHP on Packagist; and Ruby on RubyGems. The C SDK is published on crates.io. The FFI wrappers require the C library (libnexusq) to be installed locally first. See the package table and SDK guide.

What license is it under?

You can choose either the MIT license or the Apache License 2.0, the same dual license used by much of the Rust ecosystem.

How can I help?

Read the threat model, run the Arena yourself, review the code, and open an issue or a pull request. v4.1.2 is the latest GitHub release; independent external audit remains open. The known tag/assets provenance mismatch is a historical v4.1.1 issue. Security reports go through GitHub Security Advisories.
