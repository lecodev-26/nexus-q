# NEXUS-Q 4.1.1 SDK and package triage

**Status:** investigation in progress; no confirmed malicious artifact identified by the provenance evidence alone.
**Evidence snapshot:** 2026-10-25.
**Purpose:** distinguish source-identity gaps from demonstrated code defects, and prioritize follow-up without changing published artifacts.

## Executive assessment

The incident affects SDK/package trust and reproducibility: the label `4.1.1` does not identify one common source snapshot across every registry. That is not, by itself, proof that an SDK is malicious or that its cryptographic implementation is broken. The next decision must be artifact-specific, based on source diffs, build reproducibility, and independent provenance.

The first local source comparison between the GitHub-attested source commit `5dd564daab9da1c071b8b134894ea7c4eba95d09` and the commit declared by NuGet (`5b8a663b72d0d048d9f564d5650b13acdd0b8c0d`) found no changes under `bindings/`. The observed source changes are concentrated in Rust core, enrollment, kernel, server and timestamp-authority code. Many inspected changes are Rust let-chain/syntax rewrites; timestamp serial allocation was rewritten from `AtomicU64::fetch_update` to a compare-exchange loop and appears intended to preserve the checked-increment behavior. A direct byte-level comparison of the published NuGet Windows DLL and the attested GitHub release DLL now shows their entire `.text` section is identical (340,992 bytes; SHA-256 `5bea57cc82198cb3a64635ed5021f4a22a7b3dd5fce9d1f741113f10874b4286`). The files are both 410,624 bytes and differ at only 77 byte positions overall; the observed differences are PE/debug timestamps, the PDB GUID, and import hint values. Their seven exported `nexusq_*` names, imported DLL set and section layout match. This substantially narrows the discrepancy to build/link metadata rather than a difference in executable code, but it is not a reproducible-build proof and does not independently establish the NuGet package's source provenance.

A focused review of the Rust diff between those two commits covers 13 Rust files (130 insertions, 118 deletions). Most changes convert nested `if`/`if let` conditions to let-chains without an apparent change in short-circuit behavior. The notable code changes are two checked atomic serial counters (`fetch_update` replaced with a `SeqCst` load/`checked_add`/`compare_exchange_weak` retry loop), a SHAKE lane-alignment check (`% 8 == 0` to `is_multiple_of(8)`), and test/input chunk iteration (`chunks_exact` to `as_chunks`). The ML-KEM rejection sampler asserts the input length is divisible by three before using `as_chunks::<3>()`, so the remainder is expected to be empty; the output loop retains the same candidate decoding and `Q` rejection rules. Static inspection suggests these changes preserve intended behavior, but a formal equivalence check has not been run for the source split. A local offline test run on the current branch (the `nexusq-kernels`, `nexusq-tsa` and `nexusq-enrollment` trees are identical to those at `5b8a663…`) passed 53 tests: kernels 45/45, TSA 2/2, enrollment 6/6, using Rust/Cargo 1.99.1. This is not a CI result and does not validate MSRV 1.88 or 1.85 specifically.

The declared MSRV differs by source snapshot: the workspace commit `5dd564d…` declares Rust 1.85, while `5b8a663…` declares Rust 1.88. The latter source uses let-chains and `as_chunks`, consistent with the raised MSRV. The crates.io archives recorded against `5dd564d…` declare 1.85, so this is evidence of version-line drift across package channels rather than, by itself, proof that those crate manifests understate the MSRV of their own archived source. Continue checking package-by-package rather than applying one MSRV claim to every 4.1.1 artifact.

The four crates.io source revisions have also been diffed directly: `3f8dfb7…` adds no Rust crate source changes relative to `5dd564d…`; `c0899e4…` changes only the two checked serial-allocation loops in enrollment and TSA; and `38701d5…` has no `crates/` diff relative to `5b8a663…`. These source deltas appear behavior-preserving, but the self-reported source identity split remains a provenance discrepancy.

The broad SDK/runtime behavior change is between Packagist's source snapshot `b243950…` and the release-attested SDK snapshot `5dd564d…` (not between `5dd564d…` and current `main`/`84992f9…`, where the inspected binding files are unchanged). That diff touches 52 files under `bindings/` (1,576 insertions, 282 deletions). It adds version-matched native-runtime acquisition to multiple language bindings: Swift removes the `CNexusq` system-library shim and downloads/loads a runtime on macOS ARM64; TypeScript adds an npm `postinstall` downloader for Linux x64/ARM64 glibc, macOS ARM64 and Windows x64; PHP adds a runtime resolver/downloader for supported Linux/macOS/Windows targets; Go adds runtime loaders; and Dart, Java/Kotlin and Ruby also receive binding/runtime changes. .NET updates its wrapper and is packaged with RID-specific native assets by NuGet. Exact supported targets and setup paths remain language-specific and should be checked against each binding README.

This is a material install-time behavior change for several SDKs: instead of requiring users to build/install the C SDK themselves, published package installation or first use can fetch a native library, cache/package it, verify its SHA-256 against `NATIVE-RUNTIME-SHA256SUMS`, and load it. The checksum check detects corruption or a binary/manifest mismatch, but the checksum manifest is fetched from the same release origin and the installers do not independently verify the SLSA attestation. This is a provenance assurance limitation, not evidence of malicious behavior. The Packagist dist at `b243950…` therefore has older binding/runtime behavior than the later release-attested SDK snapshot under the same `4.1.1` label; the PHP source diff is additive (`Nexusq::backendInfo()` plus runtime resolution/download); root `composer.json` is byte-identical between `b243950…` and `5dd564d…`, including the PHP >=8.1 and `ext-ffi` requirements. No Composer dependency change was found in that comparison.

## Severity and response criteria

- **Confirmed:** tag/source identity divergence and multiple recorded source revisions under the same `4.1.1` label.
- **Unresolved:** whether any of those differences change security behavior; whether the NuGet Windows DLL can be reproduced; why the refs diverged; and whether every package's contents match its claimed source/build.
- **Not established:** malicious code, key compromise, exploitability, or a cryptographic break.

Do not mark a package “compromised” solely because its hash differs from another build. A hash mismatch means the bytes differ; it does not explain why. Conversely, matching a registry checksum only proves consistency with that registry's published digest, not that the artifact is safe or built from the intended source.

## Guardrails

This triage does not retarget or delete historical tags, alter published packages, publish a new version, change cryptographic behavior, or monitor CI. All follow-up is read-only until a specific corrective change is reviewed and authorized.
